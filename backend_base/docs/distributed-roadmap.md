# 分布式基础能力开发路线图

## 1. 状态与目标

本文记录后续开发方案，不在本次修改中增加运行时代码或中间件依赖。

| 阶段 | 状态 | 主要交付 |
|---|---|---|
| [V1](distributed.md) | 已实现 | Redisson 锁、Redis 固定窗口限流、短窗口防重、双实例演示 |
| [V2](distributed-v2-cache.md) | 规划，未实现 | 类型明确的缓存入口、TTL 随机化、空值缓存、热点数据加载保护 |
| [V3](distributed-v3-messaging.md) | 规划，未实现 | 单一 MQ 适配、消息契约、重试和失败处理、消费幂等扩展、可选 Outbox |
| [V4](distributed-v4-observability.md) | 规划，未实现 | 指标和链路、依赖健康、优雅停机、可复现故障验证 |

V1～V4 是能力阶段名称，不是 Maven 制品版本，也不承诺发布日期。当前 `pom.xml` 的版本不因写入路线图而改变。

目标仍是通用脚手架：JDK 17、Spring Boot 3.5.9、MyBatis-Plus、MySQL、Sa-Token，单 Maven 模块、按业务包组织。各阶段提供公共机制和接入约定，不建立商品、订单、支付等业务模型。

## 2. 共用实施约束

1. 功能默认关闭，通过独立配置启用；关闭时不创建相关客户端、后台线程、业务表或外部连接，也不要求配置未启用服务的凭据。现有 MySQL/Redis 基线保持不变。
2. 每阶段先明确 API 和故障语义，再实现适配器。文档中的拟定名称可在实现前调整，落地后同步更新使用文档。
3. 复用 V1 的环境隔离、Key 构造和统一异常约定。新增功能不能悄悄改变现有锁、限流、防重的默认行为。
4. 注解用在不支持的位置、功能开启但配置不完整时，明确报错；具体在启动期还是调用期发现，必须写清楚并测试。
5. 有界资源：加载等待、重试、线程、批量、消息大小、数据留存均设上限。故障时显式选择拒绝、降级或延后处理，不无条件重试写业务。
6. 通用组件不承诺 exactly-once、跨服务强一致或自动补偿。数据归属、数据库约束、状态机和权限判断由业务模块负责。
7. 示例放独立构建配置或测试源码，不进入默认生产包。真实 Redis、MySQL、MQ 和观测组件使用可选集成测试/演示环境，不能用 Mock 证明分布式原子性。
8. 每阶段完成时更新脚手架 README、docs 导航、配置表、错误码、接入示例、运行步骤和限制；不能仅增加一篇详细文档链接。

## 3. 推荐开发顺序

- **V2**：缓存读取契约 → 编解码和 Key → TTL/空值 → 热点加载保护 → 事务后失效约定 → 双实例测试。
- **V3**：确认 RabbitMQ 选型及消息契约 → 发布确认和手动确认 → 有界重试/失败队列 → 幂等接入 → 可选 Outbox → 故障恢复测试。
- **V4**：定义指标与标签 → HTTP/Redis/MQ 观测 → 健康探针 → 停机流程 → 观测 Compose → 故障验证脚本。

V2 可复用 V1 的锁；V3 的数据库幂等和 Outbox 不依赖 V2 缓存。V4 的基础观测也可以提前做，但不应阻塞 V2/V3 接口设计。V2/V3 实现时先保留小型统计入口，V4 再连接具体指标与链路后端，避免将业务 API 绑定到观测供应商。

每个阶段拆成可独立评审的小任务。即使同一阶段尚未全部交付，已完成子项也应标记清楚，不能把整阶段写成“已实现”。

## 4. 验收与发布要求

| 检查项 | 验收依据 |
|---|---|
| 基线兼容 | 默认配置仍能启动；V1 原有行为及测试通过；没有默认新增中间件要求 |
| 功能关闭 | 不创建对应客户端、消费者、调度线程或可选基础表 |
| 功能开启 | 缺失/非法配置有明确错误；故障路径有可预期的状态和日志 |
| 并发与恢复 | 用真实依赖验证两实例并发、超时、断连、重复请求/投递和恢复 |
| 构建隔离 | 默认生产包不含演示 Controller、演示凭据和测试组件 |
| 使用体验 | 从干净检出按 README 能完成首次调用与验收 |
| 运维边界 | 凭据、管理端口、日志脱敏、保留策略及人工处理入口有说明 |

基础构建和 V1 真实 Redis 测试继续沿用现有流程；新增 profile、脚本名称等须在实现时确定，本文不预设当前可执行的命令。
