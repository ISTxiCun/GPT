# 分布式基础能力开发路线图

## 1. 状态与目标

本文记录分布式公共能力的后续开发方案，并与[快速生成模块方案](module-generator.md)衔接。本次仅更新规划，不增加运行时代码、中间件依赖或业务模板。

| 阶段 | 状态 | 主要交付 |
|---|---|---|
| [V1](distributed.md) | 已实现 | Redisson 锁、Redis 固定窗口限流、短窗口防重、双实例演示 |
| [V2](distributed-v2-cache.md) | 规划，未实现 | 类型明确的缓存入口、TTL 随机化、空值缓存、热点数据加载保护 |
| [V3](distributed-v3-messaging.md) | 规划，未实现 | 单一 MQ 适配、消息契约、重试和失败处理、消费幂等扩展、可选 Outbox |
| [V4](distributed-v4-observability.md) | 规划，未实现 | 指标和链路、依赖健康、优雅停机、可复现故障验证 |

V1～V4 是能力阶段名称，不是 Maven 制品版本，也不承诺发布日期。当前 `pom.xml` 的版本不因写入路线图而改变。

目标仍是通用脚手架：JDK 17、Spring Boot 3.5.9、MyBatis-Plus、MySQL、Sa-Token，单 Maven 模块、按业务包组织。V1～V4 提供公共机制和接入约定，不在公共层建立商品、订单、支付等业务模型；业务模型由模块生成器的可选模板按需产生，生成业务包不增加 Maven 子模块。

### 1.1 两条实施主线

| 主线 | 阶段 | 当前状态 | 交付边界 |
|---|---|---|---|
| 分布式公共能力 | V1～V4 | V1 已实现，V2 核心已实现，V3～V4 规划中 | 锁、限流、防重及后续缓存、消息、观测机制 |
| 模块生成器 | G1～G4 | 全部为设计规划，尚未实现 | 生成内核、首批模板与勾选界面、分布式验收、模板库扩展 |

G1～G4 沿用[模块生成器实施阶段](module-generator.md#11-实施阶段与优先级)，不作为 V5，也不与 V1～V4 一一对应。18 类模块是规划中的可选模板库，不是当前已有业务模块。公共能力已实现、模板可生成、生成结果通过业务验收，是分别记录的状态。

## 2. 共用实施约束

1. 功能默认关闭，通过独立配置启用；关闭时不创建相关客户端、后台线程、业务表或外部连接，也不要求配置未启用服务的凭据。现有 MySQL/Redis 基线保持不变。
2. 每阶段先明确 API 和故障语义，再实现适配器。文档中的拟定名称可在实现前调整，落地后同步更新使用文档。
3. 复用 `ApplicationIdentity` 和 `app.identity` 作为唯一应用/环境来源，遵守[架构保护规则](architecture-guardrails.md)中的错误分层与 CORS 扩展约定，复用 V1 的 Key 构造和异常契约。新增功能不能悄悄改变现有锁、限流、防重的默认行为。
4. 注解用在不支持的位置、功能开启但配置不完整时，明确报错；具体在启动期还是调用期发现，必须写清楚并测试。
5. 有界资源：加载等待、重试、线程、批量、消息大小、数据留存均设上限。故障时显式选择拒绝、降级或延后处理，不无条件重试写业务。
6. 通用组件不承诺 exactly-once、跨服务强一致或自动补偿。数据归属、数据库约束、状态机和权限判断由业务模块负责。
7. 示例放独立构建配置或测试源码，不进入默认生产包。真实 Redis、MySQL、MQ 和观测组件使用可选集成测试/演示环境，不能用 Mock 证明分布式原子性。
8. 每阶段完成时更新脚手架 README、docs 导航、配置表、错误码、接入示例、运行步骤和限制；不能仅增加一篇详细文档链接。
9. 公共机制只维护一份；生成模板复用公共 API，不复制锁、限流、缓存或消息实现。数据库唯一约束、条件更新、状态机、事务和权限仍由业务模板及接入方负责，V1 短窗口防重不能替代持久业务幂等。
10. 新公共能力落地时同步明确模板可依赖的 API、能力标识/版本、配置和故障语义，供后续生成器能力目录检查；不将文档规划或依赖声明等同于运行环境就绪。

## 3. 推荐开发顺序

### 3.1 公共能力主线

- **V2**：缓存读取契约 → 编解码和 Key → TTL/空值 → 热点加载保护 → 事务后失效约定 → 双实例测试。
- **V3**：确认 RabbitMQ 选型及消息契约 → 发布确认和手动确认 → 有界重试/失败队列 → 幂等接入 → 可选 Outbox → 故障恢复测试。
- **V4**：定义指标与标签 → HTTP/Redis/MQ 观测 → 健康探针 → 停机流程 → 观测 Compose → 故障验证脚本。

V2 可复用 V1 的锁；V3 的数据库幂等和 Outbox 不依赖 V2 缓存。V4 的基础观测也可以提前做，但不应阻塞 V2/V3 接口设计。V2/V3 实现时先保留小型统计入口，V4 再连接具体指标与链路后端，避免将业务 API 绑定到观测供应商。

每个阶段拆成可独立评审的小任务。即使同一阶段尚未全部交付，已完成子项也应标记清楚，不能把整阶段写成“已实现”。

### 3.2 与模块生成器的协作顺序

1. **G1 可与 V2 并行**：先实现规格、模板描述、依赖/互斥解析、渲染、预览、文件保护和失败恢复。用当前 V1 能力验证目录与检查机制，V2～V4 保持未可用标记。
2. **G2 聚焦用户、库存、订单**：实现首批基础流程和 Vue 勾选/预览，优先同库事务、数据库约束、Sa-Token/Redis 与 V1 接入；首批订单超时可采用受控扫描，不强制等待 MQ 或完整任务中心。
3. **G3 验证首批分布式场景**：对共享会话、持久幂等订单、库存预占/确认/释放开展真实 MySQL/Redis 双实例测试。仅通过验收的具体功能标记 L2，不把整个模块或全部模板标为已交付。
4. **V2/V3 就绪后逐项扩展 G4**：缓存、通知可靠投递、异步下单和索引同步按实际依赖开放；支付等外部渠道另需适配与验收，不能仅因公共组件可用而宣布模板可用。
5. **V4 逐步覆盖已交付场景**：为公共机制及已实现模板补充运行指标、链路、健康和故障验证；基础日志与验证入口在前期保留，不等待 V4 才检查失败与恢复。

G4 的 P0/P1/P2 范围、18 类模块规格和生成器自身的安全写入流程以 [module-generator.md](module-generator.md) 为准；本路线图只规定公共能力与模板的衔接。

### 3.3 能力与模板依赖

| 模板场景 | 公共能力或绑定 | 开放与验收条件 |
|---|---|---|
| 用户共享会话、入口限流 | 现有 Sa-Token/Redis、可选 V1 限流 | 仍需实现账号验证、权限和跨实例会话测试；已有底座不代表已有用户模板 |
| 幂等订单、库存预占/确认/释放 | MySQL 约束与本地事务、按需 V1 | 持久请求号和业务键、合法状态转换、竞争及回滚验证；不强制依赖 V2/V3 |
| 热点查询与搜索缓存 | V2；加载保护复用 V1 锁 | V2 未实现时不可作为可运行缓存功能勾选；搜索引擎另需适配 |
| 订单延迟关闭、通知可靠投递、异步下单、事件同步 | V3 的相应 MQ 能力、业务幂等；可靠事件按方案选 Outbox | 分别验收所需投递语义和适配，V3 阶段名称不代表自动具备所有 broker 特性或业务闭环 |
| 模板运行观测与故障定位 | V4、各模板的统计/链路入口 | 覆盖实际启用组件，明确标签边界、失败状态和恢复步骤 |

生成器需分别展示模板可用性与运行依赖要求。未实现的公共能力必须明确提示并禁止选择对应可运行功能；L0 骨架可以列出待补项，但不能伪造业务成功。L1/L2、功能状态与组合约束沿用[生成器交付层次](module-generator.md#12-三种交付层次)。

## 4. 验收与发布要求

| 检查项 | 验收依据 |
|---|---|
| 基线兼容 | 默认配置仍能启动；V1 原有行为及测试通过；没有默认新增中间件要求 |
| 功能关闭 | 不创建对应客户端、消费者、调度线程或可选基础表 |
| 功能开启 | 缺失/非法配置有明确错误；故障路径有可预期的状态和日志 |
| 并发与恢复 | 用真实依赖验证两实例并发、超时、断连、重复请求/投递和恢复 |
| 构建隔离 | 默认生产包不含演示 Controller、演示凭据和测试组件 |
| 使用体验 | 从干净检出按 README 能完成首次调用与验收 |
| 模板衔接 | 公共 API、能力目录与功能状态一致；缺失能力/绑定在生成计划阶段明确拒绝；依赖仅随所选功能引入 |
| 联合验收 | 已实现模板的代表规格可生成、编译并验证；L2 按具体功能通过真实依赖的并发/故障测试，记录未覆盖组合 |
| 运维边界 | 凭据、管理端口、日志脱敏、保留策略及人工处理入口有说明 |

默认生产包还须排除生成器 UI/API、模板管理入口和本地工具认证逻辑；生成器源码/profile 与演示包分别隔离，普通业务构建不因生成界面引入 Node 必需项。生成 SQL 默认作为待审查候选，不自动执行；选择纳入 Flyway 时须提示启动执行与迁移冲突风险。具体生成与写入验收见[模块生成器验收标准](module-generator.md#12-验收标准)。

基础构建和 V1 真实 Redis 测试继续沿用现有流程；新增 profile、脚本名称等须在实现时确定，本文不预设当前可执行的命令。

## 5. 后续开发检查表

各阶段开始时复制到实际任务记录，并填写设计决定、验证结果和关联提交。

- [ ] 核实当前代码和依赖兼容性，确认本阶段范围。
- [ ] 定稿 API、配置、错误码、默认值及故障策略。
- [ ] 明确哪些保证由公共组件提供，哪些由业务实现。
- [ ] 实现默认关闭和配置校验，再接入外部组件。
- [ ] 明确受影响的模板功能、能力标识/版本和服务绑定，更新可用状态及依赖/互斥规则。
- [ ] 补齐真实依赖的并发、失败、恢复测试。
- [ ] 验证默认包、演示包与生成工具的隔离。
- [ ] 如已交付相关模板，验证代表规格的生成、编译及组合场景；未实现项保留规划标记。
- [ ] 更新 README 与 docs，并实际执行文档步骤。
- [ ] 记录限制、迁移/回滚方式，将已验收子项更新为已实现。
